# RESEARCH_COMPETITORS — рынок аналогов gwm и применимость их фич

Живой источник знания об окружении gwm, не одноразовый снимок. Собран 2026-09-04 пятью независимыми
research-агентами (WebSearch/WebFetch/GitHub API, без вложенных субагентов), заявления
верифицированы через README/официальные доки/changelog/GitHub API — не по названию проекта.
Полные сырые находки агентов (с URL на каждое утверждение) — в истории этой сессии; здесь —
синтез и выводы, обязательные к сверке с [`PLAN.md`](./PLAN.md) / [`POST_MVP_PLAN.md`](./POST_MVP_PLAN.md)
перед тем, как на этот документ ссылаться как на актуальный (рынок двигается быстрее, чем этот файл
будет перечитываться).

## 1. Методология

Три круга поиска (по решению пользователя — максимально широкий охват):

1. **Прямые аналоги** — CLI/TUI вокруг `git worktree` конкретно, плюс нативная поддержка worktree
   в IDE/GUI git-клиентах.
2. **Смежные git TUI** — не про worktree, но релевантные по UX-паттернам поверх git.
3. **Workspace/monorepo-менеджеры** — инструменты статуса/агрегации по множеству репозиториев
   ИЛИ по множеству пакетов одного репозитория.

Для каждого инструмента фиксировались: статус (жив/заброшен, дата, звёзды), точная функциональность
со ссылкой на источник, плюсы, минусы, сравнение с gwm. Правило точности: без источника — "недостаточно
данных", а не домысел по названию. Первая попытка (единый deep-research workflow с 6-7 параллельными
поисковыми агентами) дважды упала на rate-limit провайдера — переделано вручную через Agent-тул
двумя волнами по ≤3 агента одновременно (см. правило проекта об ограничении веера субагентов).

bulk-delete (`gwm`-shutootaki). Это пересечение — реальный ров (moat) продукта, не воображаемый.

### IDE / GUI git-клиенты

Проверены: VS Code (нативно с v1.103, июль 2025), JetBrains IDEs (базово с 2016, отдельная
фича «Git Worktrees» в 2026.1), Sublime Merge (частично, dev-сборка ~июль 2026), Fork (v2.17),
GitKraken (v10.5.0→12.4), Tower (12.5 Mac/9.0 Win), GitButler (нет — вместо этого «виртуальные
ветки», другая парадигма), Sourcetree (нет вообще, запрос с 2015 года).

**Все восемь — однорепозиторные.** Ни один не даёт портфельного обзора, orphan-детекции или
bulk-удаления — это подтверждает, что ниша gwm (терминальный, портфельный, офлайн) не занята ни
одним GUI-клиентом. Из интересного, чего у gwm нет: копирование gitignored-файлов (`.env`) в новый
worktree и diff-против-workspace (VS Code `git.worktreeIncludeFiles`), визуализация WIP-узлов на
графе коммитов по каждому worktree + lock/unlock (GitKraken), однокликовое «ветка → worktree»
(Tower/GitKraken).

## 3. Смежные git TUI-инструменты

lazygit (~82k★, есть панель Worktrees, `w` от ветки → создать+переключиться одним нажатием),
tig (~13.3k★, нет worktree UI, есть известный баг визуализации refs во вторичном worktree — issue
[#458](https://github.com/jonas/tig/issues/458)), gitui (~22.5k★, нет worktree-панели, но
асинхронный неблокирующий git-движок — на ядре Linux 900k+ коммитов даёт 24с/0.17ГБ без фризов),
forgit (~5.1k★, команды `gwt`/`gwa`/`gwd` — интерактивный worktree browser/add/remove через fzf с
live-preview), git-fuzzy (~2.4k★, нет worktree-фич, но dual-pane fuzzy-фильтр).

**Три переносимых UX-паттерна** (сходится независимо в нескольких инструментах — сильный сигнал):

1. **Асинхронный/потоковый скан** (gitui) — фоновые git-вызовы, рендер строки по мере готовности
   репо, а не ожидание самого медленного.
2. **fzf-фильтр + live-preview** (forgit, git-fuzzy) — тайп-ту-фильтр по worktree со preview
   branch/ahead-behind/last-commit.
3. **Панельная навигация + контекстная подсказка клавиш** (lazygit, gitui) — Tab между панелями
   репо-список/детали, нижняя строка показывает только валидные для текущей строки клавиши.

## 4. Workspace/monorepo-менеджеры

**Мульти-репо статус-агрегаторы** (ближе к проблеме gwm, чем monorepo-сборщики): Google `repo`
(манифест-XML, `forall`, никакого управления worktree), **gita** (1934★, ближайший аналог в этой
категории — цветной статус-дашборд по многим репо, но worktree-осведомлённость ограничена
регистрацией bare-репо только на чтение, без ahead/behind-счётчиков и без clean), meta (2220★,
`.meta`+plugin exec, без worktree), vcstool (503★, низкая активность, YAML-манифест с
export/import — ROS-экосистема), myrepos/mr (заморожен с 2018), gr/mixu (заброшен 2019, не
учитывается), git-xargs (жив, но другая категория — массовое открытие PR по организации, не
локальный дашборд).

**Monorepo build-инструменты** (nx, turborepo): проверено явно — решают ДРУГУЮ задачу
(task-оркестрация/кеш внутри одного репозитория с несколькими пакетами). Единственные их
«worktree»-фичи (Nx 22.7, Turborepo 2.8) — это шеринг build-кеша между worktree одного репо, не
обзор/статус. Конкурентами gwm не являются, транслируемых идей почти нет (`nx affected` философски
похож на ahead/behind, но gwm уже считает это напрямую через git).

**Вывод:** ни один инструмент этой категории не имеет lifecycle-функций gwm (orphan-детекция,
bulk-clean) — ниша подтверждённо свободна и в этом круге тоже.

## 5. Матрица применимости — что делать с находками

Оценка **только** относительно уже задокументированных границ проекта (`docs/POST_MVP_PLAN.md`
§«Границы, которые НЕ двигаем», философия §4 `PLAN.md`: офлайн, без сети/сервера, «лёгкость важнее
богатства»). Вердикт — не решение, а рекомендация; там, где это касается позиционирования продукта,
а не техники, — явно помечено как открытый вопрос пользователю (§6).

## 6. Открытые вопросы пользователю (продуктовые решения, не технические)

Это решения **не мои** — фиксирую находку и развилку, финальный выбор за автором проекта:

1. **Позиционирование вокруг AI-агентов (см. п.10 таблицы).** Явно ли gwm хочет обозначить себя
   как инструмент для параллельной работы AI-агентов (что уже фактически происходит — этот самый
   отчёт готовился в рамках работы Claude Code над этим репозиторием), или сознательно оставить
   формулировку `PLAN.md` §2/§3 нейтральной («несколько веток/фич», без уточнения источника
   параллелизма)? Это влияет на приоритет пп. 1, 2, 6, 7, 9 таблицы выше — если да, они получают
   более конкретную acceptance-формулировку («для сессии агента X»), если нет — остаются
   общечеловеческими UX-улучшениями без агентной специфики.
2. **Совпадение имени команды с `gwm` (shutootaki, Rust, github.com/shutootaki/gwm).** Пока
   `gwm` остаётся личным pet-проектом без публикации — не блокирует ничего. Но если возникнет
   намерение опубликовать (SDKMAN/Homebrew — уже упомянуто как идея в `POST_MVP_PLAN.md`
   §«Производительность/упаковка»), совпадение бинарного имени станет проблемой обнаружения.
   Вынесено отдельной background-задачей (не блокирует текущую работу).

## 7. Официальные Claude-скиллы, применимые к разработке gwm

Обзор доступных в этой среде официальных скиллов (не сторонних) с точки зрения девелопмент-пайплайна
gwm, уже описанного в `CLAUDE.md` (Opus-планирование → Sonnet-тестирование → Opus `/code-review` →
цикл исправлений → commit/push/PR).

**Уже используется, подтверждено полезным:**
- `code-review` — уже вписан в CLAUDE.md как обязательный шаг 3 независимого ревью.
- `code-docs-audit` — использован в этой самой сессии, нашёл реальный дрейф (`PLAN.md` отставал
  на два Этапа). Стоит формализовать как периодический шаг, а не разовое действие — например,
  запускать после каждых 2–3 смерженных Этапов (перекликается с уже сохранённой памятью
  «README тихо устарел за 3 смерженных Этапа»).

**Рекомендуется добавить:**
- `security-review` — не используется ни разу за всю историю проекта, хотя поверхность реальна:
  `GitCommand` шеллится через `ProcessBuilder`, `config/TomlLite.kt` — самодельный парсер,
  `--print-path`/`gwm cd` фидит вывод прямо в `cd "$(...)"` шелл-обёртки. Локальный инструмент не
  освобождает от базовой гигиены (path traversal в конфиге, некорректная обработка спецсимволов в
  именах веток/путей). Рекомендация — прогнать один раз как baseline, затем при каждом Этапе,
  трогающем `git/`, `config/` или `ui/ShellInit.kt`.
- `verify` — формализует уже существующее в `CLAUDE.md` требование «смотреть на реальное поведение,
  не только на код» для TUI/CLI-фич; сейчас это делается вручную и неформально.
- `run` — быстрый запуск/скриншот собранного `gwm` для финального шага 6 пайплайна («финальный
  зелёный прогон... глазами на поведении»).

**Опционально, не приоритет:**
- `simplify` — периодическая чистка Kotlin-кода (reuse/эффективность), не пересекается по духу
  с `code-review` (тот про баги).
- `fewer-permission-prompts` — снизить трение повторяющихся разрешений на `./gradlew build`/`test`
  в этом соло-воркфлоу.

**Не применимо к этому проекту:** `claude-api` (нет интеграции с Claude API в самом gwm), `docx`/
`pptx`/`xlsx`/`pdf`/`artifact-design` (не документо-ориентированный продукт), `claude-code-guide`,
`keybindings-help` (это про клавиши самого Claude Code, не про TUI gwm), `deep-research` (разово
использован для этого отчёта, не входит в регулярный цикл разработки).
