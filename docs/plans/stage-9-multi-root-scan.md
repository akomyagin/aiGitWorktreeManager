# План Этапа 9 — «Реальный мульти-корневой `scan`»

Ветка: `stage/9-multi-root-scan` (уже создана от `master`). PR в `master` по workflow из `CLAUDE.md`
(Opus план+код → Sonnet тесты → Opus `/code-review` → до 3 итераций). **Fable не используется.**
Исполнитель плана — тот же Opus-агент по этому файлу, без доп. вопросов.

---

## 1. Цель

Реализовать реальный мульти-корневой `scan`: сканировать **все существующие** корни из
`config.roots` одновременно и агрегировать worktree всех репозиториев из всех корней в
**один** вывод — с сохранением инвариантов группировки по репо (Этап 8 PR2) и деградации
ширины таблицы (Этап 7 / Этап 8 PR3).

Сейчас несоответствие между обещанием конфига и поведением: `config.roots` — массив, но код
использует только `roots[0]` (первый *существующий* путь как тихий fallback-корень —
`GwmConfig.primaryRoot()`, `Main.kt:314-315`, `Main.kt:326`). Второй и далее путь пользователя,
вписанный в конфиг, молча игнорируется. Этот этап закрывает пункт «Мульти-корень» из
`docs/POST_MVP_PLAN.md:41`.

### Пусковой критерий мульти-корня (главное решение)

Мульти-корень включается **только когда ни один CLI-источник корня не задан** (нет позиционного
`ROOT`, нет `scan --root`, нет корневого `gwm --root`) **и** не задан `$GWM_ROOT`. В этом случае
`scan` берёт **все существующие** пути из `config.roots`. Любой явный CLI-ввод или `$GWM_ROOT`
остаётся **однокорневым** override — явный пользовательский ввод = один конкретный корень, это
разумно и сохраняет обратную совместимость.

## 2. Границы — что НЕ делать

- **Не трогать сортировку/порядок вывода.** Порядок остаётся: корни в порядке `config.roots`
  (как задал пользователь), внутри корня — репо по имени (`RepoScanner.findRepos` уже сортирует),
  внутри репо — worktree как отдал git. Никакой глобальной пересортировки по имени репо через
  корни (иначе сломается инвариант группировки — см. Р4). Глобальная сортировка — отдельный
  отложенный пункт `POST_MVP_PLAN.md`.
- **Не делать батчинг git-вызовов** (`git for-each-ref` вместо `rev-list`+`log`) — отдельный
  пункт `POST_MVP_PLAN.md` (§Производительность). Параллелизм остаётся по репо, как в Этапе 4.
- **Не добавлять `--format=json`** и любой другой формат вывода.
- **Не делать `list` многокорневой.** `list` принимает конкретный путь одного репозитория
  (`--repo`, дефолт `.`) — это операция над одним репо, мульти-корень её не касается. `interactive`,
  `create`, `remove` — тоже строго однорепозиторные, не трогать. См. Р6.
- **Не менять формат/парсер конфига** (`config/TomlLite.kt`, `GwmConfig.from`) — `roots` уже
  парсится как `List<String>`. Меняется только *использование* массива, не его чтение.
- **Не менять `RootSelection`-семантику для CLI-источников** — конфликт разных CLI-корней
  по-прежнему → `CliktError` (Этап 7). Мульти-корень живёт ниже этого гейта, только когда CLI
  ничего не дал.
- **Не менять `--print-path`.** Он использует `ScanService().scan(repos)` через
  `RepoScanner.resolveRoot` + `findRepos` (`Main.kt:122-146`, `PrintPath.emit`). Приведение его к
  мульти-корню — желательно для консистентности, но выходит за рамки минимальной задачи и
  рискует затронуть shell-контракт. **Решение: оставить `--print-path` однокорневым в этом
  этапе**, зафиксировать это явно в KDoc и в разделе техдолга плана (Р7). (Если ревью настоит —
  можно переиспользовать новую функцию сбора репозиториев из Р3; но по умолчанию — не трогаем.)

## 3. Принятые решения (и почему)

### Р1. Мульти-корень как отдельная явная развилка, ниже гейта `RootSelection`

Текущий `ScanCommand.run()` (`Main.kt:293-346`) устроен так:
1. `RootSelection.choose(...)` сводит три CLI-источника к одному значению или `Conflict → CliktError`.
2. Результат `chosen: String?` (null = CLI ничего не дал).
3. Тихий fallback: `configRoot = globals?.config?.primaryRoot()` (это `roots[0]`-существующий).
4. `resolveRoot(chosen, configRoot)` → один `rootDir`, `findRepos(rootDir)` → сканируется один корень.

Новая логика вставляется **между шагом 2 и шагом 4**, как явная развилка:

- Определить, есть ли какой-либо однокорневой override:
  `hasSingleRootOverride = chosen != null || !System.getenv("GWM_ROOT").isNullOrBlank()`.
- **Если override есть** — поведение НЕ меняется относительно Этапа 8: один корень через
  `resolveRoot(chosen, configRoot=null)` (см. ниже про configRoot), `findRepos`, сканирование
  одного корня. (В этой ветке `config.roots` вообще не участвует — override главнее.)
- **Если override нет** — мульти-корневая ветка:
  - Собрать список существующих корней из `config.roots` (Р3, `MultiRootSelection.resolveScanRoots`).
  - Если существующих корней ≥ 1 — сканировать их **все**, агрегировать в один вывод (Р3/Р4).
  - Если `config.roots` пуст (нет конфига / пустой массив) — поведение как сейчас: единственный
    корень = `resolveRoot(null, null)` = `RepoScanner.defaultRoot()` (`~/Projects/ai-projects`).
    Это ровно обратная совместимость «пустой roots» (Р8).
  - Если `config.roots` непуст, но **ни один** путь не существует — предупредить (жёлтым, stderr,
    exit 0) и упасть на дефолтный корень. Это сохраняет и обобщает существующее предупреждение
    `Main.kt:319-325` (было для «roots заданы, primaryRoot==null»).

**Почему отдельная развилка, а не расширение `RootSelection`:** `RootSelection` намеренно про
**CLI-конфликты** (три источника, разные значения → ошибка) и возвращает *один* `String?`.
Мульти-корень — это множество корней из *тихого fallback*-слоя, который по решению Этапа 8
(`RepoScanner.resolveRoot` KDoc, `SKILL.md` «Тихий fallback ≠ отсутствие диагностики»)
**не участвует в конфликт-детекции**. Смешивать «конфликт явных вводов» и «объединение тихих
fallback-корней» в одном типе — испортить обе роли. Поэтому новый маленький объект
`MultiRootSelection` рядом с `RootSelection`, а не правка последнего.

### Р2. `configRoot` больше не нужен в однокорневой ветке `scan`

Сейчас `resolveRoot(chosen, configRoot)` подмешивает `primaryRoot()` (=`roots[0]`) как fallback
даже когда `chosen != null`? Нет — `resolveRoot` возвращает по приоритету override → env → config →
default, так что при `chosen != null` config не смотрится. Но при `chosen == null` старый код
использовал `configRoot` (=`roots[0]`). В новой логике этот случай (`chosen == null` и нет env)
уходит целиком в мульти-корневую ветку, где `config.roots` обрабатывается явно и полностью.

Поэтому в **однокорневой** ветке вызов становится `resolveRoot(chosen, configRoot = null)` —
config-fallback там больше не нужен (либо `chosen != null`, либо `$GWM_ROOT` задан; и то и другое
главнее config по определению этой ветки). Это упрощение, не изменение поведения: единственный
путь, где раньше срабатывал `configRoot`, теперь обслуживается мульти-корневой веткой (которая для
одного существующего корня даёт тот же результат — см. Р8, кейс «один путь в roots»).

`GwmConfig.primaryRoot()` **остаётся** — им продолжает пользоваться `PrintPath.emit`
(`Main.kt:103`), который в этом этапе не трогаем. Не удалять.

### Р3. Сбор репозиториев из нескольких корней + дедупликация

Новый чистый объект `scan/MultiRootSelection.kt` (по образцу `RootSelection.kt` — чистая логика,
без git, юнит-тестируемая, ФС-доступ только для проверки существования каталогов):

```kotlin
package dev.alkom.gwm.scan

import java.io.File

/** Результат разбора config.roots в набор реально существующих корней сканирования. */
data class ScanRoots(
    /** Существующие корни в порядке config.roots, дедуплицированные по канон. абсолютному пути. */
    val roots: List<File>,
    /** Сконфигурированные, но несуществующие/недоступные пути — для предупреждения (Р5). */
    val missing: List<String>,
)

object MultiRootSelection {
    /**
     * Разбирает config.roots в существующие корни (с `~`-раскрытием через RepoScanner.expandTilde),
     * сохраняя порядок и дедуплицируя по канон. абсолютному пути (absoluteFile.normalize()).
     * Пустые/пробельные записи игнорируются. Чистая логика; ФС только для File.isDirectory.
     */
    fun resolveScanRoots(
        configRoots: List<String>,
        home: String = System.getProperty("user.home"),
    ): ScanRoots
}
```

Реализация: пройти `configRoots`, для каждой непустой записи `expandTilde` → `File(...).absoluteFile
.normalize()`; если `isDirectory` — в `roots` (с дедупликацией по `.path` через `LinkedHashSet`,
чтобы держать порядок); иначе — сырое значение в `missing`. Дедупликация по **каноническому**
пути закрывает: повтор одного пути в конфиге, и два разных строковых написания одного каталога
(`/x` и `/x/`, `~/p` и `$HOME/p`). Символические ссылки не разрешаем (`canonicalFile` не берём —
он делает лишний ФС-hit и может по-разному вести себя на разных ФС; `normalize()` достаточно для
описанных кейсов, а полное разрешение симлинков в границы задачи не входит).

**Дедупликация репозиториев поверх дедупликации корней (второй уровень).** Даже с уникальными
корнями один и тот же репозиторий может быть достижим из двух корней (например, вложенные корни
`~/Projects` и `~/Projects/ai-projects`, или симлинк). Поэтому после `findRepos` по всем корням —
дедуплицировать **репозитории** по каноническому абсолютному пути каталога репо. Реализуется в
новом методе `ScanService` (Р4), а не в `MultiRootSelection`, т.к. это про список репо, а не корней.

`RepoScanner` не меняем — `findRepos(root)` уже даёт репозитории одного корня, отсортированные по
имени. Мульти-корневой сбор — это `roots.flatMap { RepoScanner.findRepos(it) }` с последующей
дедупликацией. Порядок: корни в порядке config → внутри каждого репо по имени. НЕ сортировать
глобально (сохраняет группировку — Р4, и границу «не трогать сортировку» — §2).

### Р4. Агрегация в один вывод: инвариант группировки и дедуп репо

`ScanService.scan(repos)` уже принимает **плоский** список репозиториев и агрегирует их через
`flatMap` по репо (каждый репо — непрерывный блок worktree). Мульти-корень идеально ложится: собрать
плоский список репо из всех корней (Р3), дедуплицировать, отдать существующему `scan`. Один вывод
получается автоматически.

**Инвариант группировки (Этап 8 PR2, `SKILL.md`):** `WorktreeTable.rowsAggregated` схлопывает
имя репо на 2-й+ строке *соседних* строк одного репо. Он держится на том, что worktree одного репо
идут непрерывным блоком. `flatMap` по репо это сохраняет — **при условии**, что в списке репо нет
двух записей с одинаковым отображаемым именем, разнесённых по списку. Отсюда два требования к
дедупликации:

1. **Дедуп по каноническому пути** убирает физически один и тот же репо, достижимый из двух корней
   (иначе его worktree появились бы дважды и, если между ними попал другой репо с тем же именем —
   группировка бы «съехала»).
2. **Коллизия имён разных репо из разных корней** (например `~/work/foo` и `~/personal/foo` — два
   *разных* репо с именем `foo`). Это НЕ дубликат (разные канон. пути), оба должны попасть в вывод.
   Но группировка `WorktreeTable` завязана на **имя** (`OverviewRow.repo` — строка), и два блока
   `foo` окажутся в разных местах списка (между ними — репо из первого корня по алфавиту, идущие
   после `foo` первого корня, и репо второго корня до `foo`). Тогда имя `foo` напечатается дважды
   как два разных group-start — это визуально корректно (два *разных* репо `foo`), НЕ «съезд»
   группировки: каждый блок по-прежнему непрерывен, group-start считается по смене соседнего repo,
   а между двумя блоками `foo` есть строки с другим repo. **Проверить тестом** (Р тест-кейсы), что
   вывод в этом случае осмысленный и не падает. Улучшать различение (например `parentDir/foo`) —
   **вне границ этапа**; зафиксировать как техдолг (Р7), т.к. это редкий кейс и его решение — часть
   более общего вопроса «уникальные подписи репо», связанного с отложенной глобальной сортировкой.

**Реализация дедупликации репо — в `ScanService`**, новым публичным методом, чтобы `Main.kt`
оставался тонким и дедуп был юнит-тестируем:

```kotlin
// scan/ScanService.kt — новый метод
/**
 * Дедуплицирует репозитории по каноническому абсолютному пути каталога, сохраняя порядок
 * первого появления. Нужно для мульти-корня: один физический репо, достижимый из нескольких
 * корней, не должен агрегироваться дважды. Чистая логика (только absoluteFile.normalize()).
 */
fun dedupRepos(repos: List<File>): List<File>
```

Затем `ScanCommand` делает `ScanService().scan(ScanService.dedupRepos(allRepos))` — или, если
удобнее, дедуп встроить в начало `scan(repos)`. **Решение: отдельный метод `dedupRepos`,
вызываемый в `ScanCommand`**, а не внутри `scan()` — чтобы не менять контракт `scan()` для
существующих тестов/вызовов (`PrintPath` тоже зовёт `scan`, а там дедуп по одному корню не нужен и
безвреден, но явный вызов в `ScanCommand` держит изменение локальным). Метод можно сделать
`companion object` / top-level, чтобы звать без экземпляра.

### Р5. Изоляция ошибок и предупреждения

Три уровня изоляции, все — предупреждение (жёлтым, stderr через `terminal.println`, exit остаётся 0),
не падение всего `scan`:

1. **Несуществующий корень из `config.roots`** — попадает в `ScanRoots.missing`. Если после разбора
   `roots` непуст (есть хоть один рабочий корень) — предупредить о пропущенных (`⚠ пропущены
   несуществующие корни из конфига: <список>`) и продолжить по существующим. Если `roots` пуст (ВСЕ
   отсутствуют) — предупредить и упасть на дефолтный корень (обобщение `Main.kt:319-325`).
2. **Сломанный/нечитаемый репозиторий** — уже изолирован в `ScanService.aggregateOne` через
   `runCatching` → `RepoError`, выводится отдельно (`Main.kt:343-345`). Мульти-корень это не меняет —
   тот же механизм работает поверх репо из всех корней.
3. **Пустой результат** — если после сбора по всем корням репозиториев нет, вывести
   `Git-репозитории не найдены в: <корни>` (перечислить корни) и вернуться (как `Main.kt:331-334`,
   но с перечнем корней вместо одного).

**Exit-код контракт (`SKILL.md` «Exit-коды»):** все ветки-предупреждения — `terminal.println` +
продолжение/`return`, exit 0 (это диагностика, не отказ). Единственный отказ (`CliktError`,
non-zero) остаётся прежним: конфликт CLI-корней (`RootSelection.Conflict`) и сломанный конфиг
(`GwmConfig.load` в `Gwm.run`). Отсутствие/недоступность fallback-корней — не отказ (как и раньше).

### Р6. Заголовок вывода `scan` для нескольких корней

Сейчас: `Портфель: <root> (<n> репо)` (`Main.kt:336`). Для мульти-корня:
- Один корень (override или единственный существующий из config, или дефолт) — формат без изменений.
- Несколько корней — `Портфель: N корней, M репо` и, строкой ниже, перечислить корни
  (`  <root1>`, `  <root2>`, ...), чтобы пользователь видел, что реально сканировалось. Точную
  формулировку выбрать в коде; главное — не молчать о множественности.

`base` для `WorktreeTable.renderAggregated` (относительные пути) сейчас — единственный `rootDir`
(`Main.kt:339`). При нескольких корнях единого базового каталога нет. **Решение:** при нескольких
корнях передавать `root = null` в `renderAggregated` — тогда `PathDisplay.shorten` даст `~/...`
или абсолютный путь (не относительный), что корректно для путей из разных корней; колонка REPO при
выбросе допишет `<repo>: ` к неотносительному пути (уже реализовано, Этап 7/8). Проверить, что при
`base = null` таблица и деградация ведут себя корректно (тест). При одном корне — `base = тот
корень` (как сейчас, относительные пути читаемее).

### Р7. Техдолг (зафиксировать в конце этапа, Р «Финальный просмотр»)

- `--print-path` остаётся однокорневым (использует `roots[0]` через `primaryRoot`), тогда как
  `scan` — многокорневой. Расхождение осознанное (границы задачи, риск shell-контракта). Кандидат
  на выравнивание отдельным этапом.
- Различение одноимённых репо из разных корней (`~/work/foo` vs `~/personal/foo`) в группировке —
  оба печатаются как `foo`. Часть более общего вопроса «уникальные подписи репо», связанного с
  отложенной глобальной сортировкой. Не решаем здесь.
- Симлинки: дедуп по `normalize()`, не по `canonicalFile` — два корня, один из которых симлинк на
  другой, не дедуплицируются на уровне корней (но репо-дедуп по `normalize()` их тоже не поймает,
  если пути различаются). Осознанно вне границ.
- Канонизация путей (`absoluteFile.normalize()`) реализована похожим образом в 4 разных местах:
  `RootSelection.normalize`, `MultiRootSelection.resolveScanRoots`, `GwmConfig.primaryRoot`,
  `ScanService.dedupRepos` — найдено независимым ревью после реализации Этапа 9. Осознанно не
  унифицируется в цикле фиксов после ревью (план Этапа 9 явно запрещал трогать `RootSelection.kt`);
  кандидат на извлечение общей утилиты отдельным рефакторингом.

### Р8. Обратная совместимость (проверить тестами явно)

- **Нет конфига / `config.roots` пуст** — `scan` без CLI-корня идёт на дефолтный корень
  `~/Projects/ai-projects`. Ровно как Этап 8. (Мульти-корневая ветка с пустым `roots` → дефолт.)

## 6. Тест-кейсы

### Юнит — `MultiRootSelectionTest.kt` (новый, без git)
- `resolveScanRoots` с двумя существующими `@TempDir` → оба в `roots`, `missing` пуст, порядок сохранён.
- Дубликат одного пути (`["/x", "/x"]`, оба существуют) → один в `roots`.
- Два написания одного каталога (`/x` и `/x/`, или `~/p` и абсолютный `$HOME/p`) → один в `roots`.
- Несуществующий путь → в `missing`, не в `roots`.
- Смесь: `[существующий, несуществующий, существующий-дубликат]` → `roots` = [существующий],
  `missing` = [несуществующий].
- Пустой/пробельный элемент игнорируется (не в `roots`, не в `missing`).
- Пустой `configRoots` → `roots` пуст, `missing` пуст.
- `~`-раскрытие: `~/...` с реально существующим подкаталогом `$HOME` (или через параметр `home`,
  указывающий на `@TempDir`) → раскрывается и попадает в `roots`.
