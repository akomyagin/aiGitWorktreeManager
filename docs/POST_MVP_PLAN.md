# POST_MVP_PLAN — aiGitWorktreeManager (gwm)

Границы MVP и идеи «на потом». Ничего отсюда не реализуется без явного запроса — это roadmap, а не бэклог обязательств. MVP (Этапы 0–6) закрывает: обзор worktree по всем репозиториям, orphaned-детекцию, create/remove, переключение. Этап 7 сделал обзор читаемым на терминале любой ширины. Этап 8 (тремя PR) добавил конфиг-файл, группировку `scan` и колонки ahead/behind + возраст. Этап 9 сделал `scan` и `--print-path`/`gwm cd` реально мульти-корневыми. Этап 10 добавил bulk-удаление orphaned (`gwm clean`). Идеи ниже, отмеченные `~~зачёркнуто~~ **Сделано (Этап N).**`, уже реализованы — они остаются здесь как история решений.

## Явно ЗА границами MVP

- **Автоудаление orphaned worktree.** `gwm` в MVP только помечает и подсказывает; он никогда не удаляет worktree без явного действия пользователя. Автоочистка (даже опциональная) — сознательно отложена, чтобы не потерять незакоммиченную работу.
- **Не-git VCS** (Mercurial, jj/Jujutsu). Только git worktree.
- **Windows.** MVP таргетирует Linux/macOS (POSIX-шелл для cwd-обёртки). Windows-поддержка — отдельный вопрос (PowerShell-функция вместо bash-обёртки).

### Скрипты и интеграция
- **`--format=json` / `--porcelain` для `scan`/`list`.** Машиночитаемый вывод для скриптов и интеграций (в духе самого git). Осознанно НЕ сделано в Этапе 7: единственный машинный контракт сейчас — `--print-path` (сырой абсолютный путь). Табличный вывод остаётся человекочитаемым; структурированный формат добавлять, когда появится конкретный потребитель (дашборд, CI-скрипт).

### Функциональность
- **Создание worktree из удалённой ветки** (`git worktree add --track -b ...`) одним действием, включая fetch. Идея согласована, готова к реализации; ниже — постановка, достаточная для холодного агента.
  - **Что делает.** `gwm create <branch>` сейчас всегда создаёт НОВУЮ локальную ветку от `--base` (дефолт `HEAD`) — см. `WorktreeService.add(path, newBranch, baseRef)` и `CreateCommand` в `Main.kt`. Нужен режим «завести worktree на СУЩЕСТВУЮЩУЮ удалённую ветку `origin/<branch>` с локальным трекингом», по аналогии с `git worktree add --track -b <branch> <path> origin/<branch>`.
  - **Точки, которые трогать.**
    - `git/WorktreeService.kt` — новый метод (например `addTracking(path: File, branch: String, remote: String = "origin"): GitResult`), собирающий `git worktree add --track -b <branch> <path> <remote>/<branch>`; отдельный метод `fetch(remote: String = "origin"): GitResult` = `git(repoDir, listOf("fetch", remote))`. Не менять сигнатуру существующего `add` — добавить рядом, чтобы не задеть Этап 2.
    - `Main.kt`, `CreateCommand` — новый флаг `--track` (`by option("--track").flag()`), взаимоисключающий с `--base` (если оба заданы → `CliktError`). При `--track`: сперва `service.fetch()` (по умолчанию `origin`), затем `addTracking(target, branch)`. Дефолтный путь берётся тем же `defaultWorktreePath(branch, template)`, что и сейчас.
    - Тесты — `WorktreeServiceIntegrationTest.kt` (интеграционный, реальный временный репо с фейковым `remote` из второго `@TempDir`) + командный тест взаимоисключения флагов по образцу `CleanCommandTest.kt`.
  - **Критерий готовности.** `gwm create feature-x --track` в репо с `origin/feature-x` создаёт worktree на локальной ветке `feature-x`, отслеживающей `origin/feature-x`; при отсутствии `origin/<branch>` после fetch — `CliktError` с дословным git-stderr (контракт «не глотаем ошибку git», SKILL «Exit-коды»); `./gradlew build` зелёный.
  - **Открытые продуктовые решения (за пользователем, НЕ выдумывать):** (1) имя remote — фиксировать `origin` или дать флаг `--remote`; (2) делать ли `fetch` всегда или только при промахе локального резолва `origin/<branch>`; (3) поведение, если локальная ветка `<branch>` уже существует (ошибка git как есть vs. отдельная проверка/подсказка).
- ~~**Bulk-операции:** удалить все orphaned за раз (с обязательным подтверждением каждого dirty).~~ **Сделано (Этап 10).** Команда `gwm clean`. Портфельный охват через переиспользование `MultiRootSelection` (тот же fork, что у `scan`/`--print-path`: явный CLI-корень/`$GWM_ROOT` → single-root override, иначе мульти-корень по `config.roots`). UX: показ полного списка кандидатов (`orphan.isOrphaned && !isMain`, main исключён явно в `BulkCleanPlan.from`) → агрегированный gate (`YesNoPrompt`/`--yes`) → построчное удаление. Dirty защищён ОТДЕЛЬНО: без `--force` — пропуск; с `--force` — per-item `YesNoPrompt` в TTY либо пара флагов `--yes --force`; одно общее «да» dirty никогда не удаляет (`decideDirtyConsent` — именованная чистая функция, юнит-тестируема). `--dry-run` печатает честный (по факту `--yes`/`--force`) прогноз без удаления и без запроса. Все удаления — через `WorktreeService.safeRemove` (настоящий `git worktree remove`, повторная проверка dirty на момент удаления). Частичный отказ не прерывает цикл: сводка «Удалено/пропущено/уже удалены/ошибок» + non-zero exit (`CliktError`) при git-ошибке; «нечего удалять»/«отменено»/`--dry-run` → exit 0. Группировка удаления по каталогу репо (один `git worktree list` на repoDir, дальше сопоставление в памяти) корректна при одноимённых репо из разных корней и не квадратична по числу кандидатов (найдено на независимом ревью). Логика — `scan/BulkCleanPlan.kt` (чистый отбор кандидатов) + `ui/CleanReport.kt` (чистое форматирование) + `CleanCommand` в `Main.kt`.
- **Интеграция с `aiProjectDashboard`** — экспорт обзора worktree как данных для дашборда проектов портфеля.
- **Хуки:** запускать команду после создания worktree (например, `direnv allow`, копирование `.env`).

### Производительность / упаковка (git-вызовы)
- **Батчинг ahead/behind + возраста через `git for-each-ref`.** Сейчас (Этап 8, PR 3/3) `WorktreeService.withAheadBehindAndAge` делает 2 git-вызова НА КАЖДЫЙ worktree (`rev-list` + `log -1`). Найдено на независимом ревью: `git for-each-ref --format='%(committerdate:unix) ...' refs/heads/` вернул бы обе метрики для ВСЕХ веток репо ОДНИМ вызовом (как уже сделано для `mergedBranches` в orphan-детекции). Осознанно НЕ сделано в PR 3/3: реальный замер на портфеле (25 репо/33 worktree) не показал регресса (~1.4с, как и без этих колонок) — параллелизм по репо (Этап 4) уже поглощает лишние процессы. Возвращаться сюда, если портфель вырастет настолько, что регресс станет заметен на практике, а не по теории.

### Производительность / упаковка
- **GraalVM native-image** — мгновенный старт без JVM, один бинарь. Оправдано, только если холодный старт JVM (~0.3–0.5 с) начнёт реально мешать в повседневном использовании.
- **AppCDS** — более лёгкий способ ускорить старт JVM без перехода на native.
- **Distribution:** публикация как SDKMAN-кандидат / Homebrew formula, если инструментом захотят пользоваться другие.

## Границы, которые НЕ двигаем

- Никакой сети, никакого сервера, никакой телеметрии. Инструмент остаётся полностью локальным и офлайн.
- `gwm` не пишет в `.git` напрямую — всегда через настоящий `git`.
- Не редактирует dotfiles пользователя сам — только предлагает готовый сниппет shell-функции.
