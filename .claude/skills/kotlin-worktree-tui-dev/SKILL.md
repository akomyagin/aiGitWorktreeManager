# kotlin-worktree-tui-dev — aiGitWorktreeManager (gwm)

Специфика **этого** проекта, не общий туториал по Kotlin CLI. Обоснования — `docs/TECHNICAL_PLAN.md`.

## Ядро продукта: обёртка над настоящим git, не замена

`gwm` **ничего не пишет в `.git` напрямую**. Каждая операция (list/add/remove/prune) — вызов установленного у пользователя `git` через `ProcessBuilder`. Причина — точное соответствие семантике worktree (locks, prune, prunable-флаги, `--porcelain`-форматы) и лёгкость (не тянем JGit). При ошибке git — показывать его `stderr` дословно, не «глотать».

## Обёртка над git: `GitCommand` (ProcessBuilder)

- Единая точка запуска — `GitCommand.run(workingDir, vararg args, timeoutSeconds)`. **Всегда** явная рабочая директория и **всегда** таймаут (дефолт 30 с) с `destroyForcibly()` — зависший git не должен фризить TUI.
- stdout/stderr **разделены** (`redirectErrorStream(false)`), возвращаются в `GitResult(exitCode, stdout, stderr)`; `ok = exitCode == 0`.
- Предпочитать **машинные форматы**: `--porcelain`, при списках путей — `-z` (NUL-разделители), а не человекочитаемый вывод (колоночное выравнивание брезгливо парсится).
- Не строить shell-строку и не запускать через `sh -c` — передавать аргументы списком (нет проблем с экранированием/инъекцией путей с пробелами).

## Парсинг `git worktree list --porcelain`

Формат — записи, разделённые пустой строкой; в записи строки `ключ значение`, булевы атрибуты — голым ключом:
```
worktree /path
HEAD <sha>
branch refs/heads/<name>
locked            # или: detached / bare / prunable <reason>
```
- Парсер (`WorktreeParser.parse`) — **чистая функция** `String -> List<Worktree>`: не знает ни про процессы, ни про терминал. Это самая хрупкая логика → покрывается юнит-тестами исчерпывающе (main/linked/detached/bare/prunable/пустой ввод).
- `branch` — снимать префикс `refs/heads/`. Первая запись — всегда main (primary) worktree (`isMain = index == 0`).
- Разделять записи по `\r?\n\r?\n` (устойчиво к CRLF), внутри — по строкам, `key = substringBefore(' ')`, `value = substringAfter(' ')`.

## Слои (держать раздельно, тестировать раздельно)

- `git/` — доменная модель (`Worktree`), чистый парсер (`WorktreeParser`), обёртка процесса (`GitCommand`), операции над одним репо (`WorktreeService`: list/withDirtyFlags/add/remove/prune).
- `scan/` (Фаза 2) — обход корня репозиториев (`~/Projects/ai-projects/*`, конфигурируемо), агрегация worktree всех репо, orphaned-эвристики. Параллелить через coroutines.
- `ui/` (Этап 1+) — интерактивные экраны Mordant. UI-слой **тонкий**: вся логика — в `git/`/`scan/`, чтобы её можно было тестировать без TTY.

**Правило:** чистая логика (парсинг, скоринг orphaned) не должна зависеть от I/O. `dirty`-статус наполняется отдельным шагом (`withDirtyFlags`), т.к. `git status` — дорогая часть; дешёвый `list` отдаётся первым.

## TUI: Mordant + Clikt

- **Clikt** — подкоманды/аргументы/help (`Gwm().subcommands(ListCommand(), ...)`). Тексты help — на русском (пользовательские), код — на английском.
- **Mordant** — рендеринг: `table { header {} body {} }`, цвета (`TextColors`), стили (`TextStyles.bold`), интерактивный выбор (`interactiveSelectList`, prompt). Для MVP хватает line-oriented интерактивности; full-screen (alternate screen) — post-MVP, не усложнять раньше времени.
- Для `./gradlew run` в `build.gradle.kts` проброшен `standardInput = System.in`, иначе Mordant не читает реальный терминал.
- Статусы: `✓ clean` (green) / `● dirty` (yellow) / `?` (gray, если не проверяли). main-worktree — `bold`.

## Переключение cwd

Дочерний процесс не может сменить cwd родительского шелла (POSIX). Решение: режим `--print-path` (печать **только** пути в stdout) + shell-функция-обёртка `gwm()` в `.bashrc`, которую пользователь ставит один раз (`gwm shell-init` печатает готовый сниппет). `gwm` **не редактирует dotfiles сам**. Детали — `docs/TECHNICAL_PLAN.md` §5.

## Разрушающие действия

`gwm` **никогда не удаляет worktree сам** — даже orphaned. Удаление — только по явному подтверждению пользователя в TUI. Dirty worktree удаляются с `--force` только после отдельного явного согласия. Orphaned-детекция — это **подсказка человеку**, не автоочистка.

## Exit-коды: контракт для shell-скриптов

Каждая CliktCommand должна сигнализировать неудачу через `throw CliktError("...")`, **не** через `terminal.println(...) + return`. Второе печатает предупреждение, но exit-код остаётся 0 — скрипт вокруг `gwm` (`&&`-цепочки, проверка `$?`) не увидит ошибки. Эталон — `PrintPath.emit` (Main.kt): все терминальные ветки (`Match.None`, `Match.Ambiguous`) бросают `CliktError`, только успех возвращает обычный `println` на stdout. Все команды (`list`/`create`/`remove`/`scan`) должны следовать тому же контракту для любой ветки-отказа (repo не git, target не найден, dirty без `--force`, ошибка git).

## Mordant `table {}`: приоритет ширины колонок и многоточие при обрезке

Не задокументировано нигде явно (нет sources jar в кеше Gradle для 3.0.1 — проверялось через декомпиляцию), но проверено эмпирически:

- Колонки по умолчанию (`ColumnWidth.Auto`) при нехватке места режутся с потерей содержимого без индикатора — в т.ч. режется даже заголовок колонки. Чтобы отдать приоритет «важной» колонке (например, `Путь`, ради которой вообще смотрят в `scan`/`list`), задать ей `column(i) { width = ColumnWidth.Expand() }` — тогда остальные Auto-колонки остаются по содержимому, а Expand-колонка забирает остаток и обрезается первой.
- `OverflowWrap.ELLIPSES` **не работает**, если не выставлен явно `whitespace = Whitespace.NORMAL` на той же колонке/таблице — ячейки таблицы по умолчанию `Whitespace.NOWRAP` (`wrap = false`), а условие показа «…» в Mordant — `whitespace.wrap && cellWidth > wrapWidth`. Без этого текст обрезается молча, без «…». Нужны оба свойства вместе:
  ```kotlin
  column(pathIndex) {
      width = ColumnWidth.Expand()
      whitespace = Whitespace.NORMAL
      overflowWrap = OverflowWrap.ELLIPSES
  }
  ```
- Fallback-ширина для недетектируемого/непривязанного к TTY вывода (pipe, `TERM=dumb`, CI-логи) по умолчанию у Mordant — ~79 колонок. Конструировать `Terminal(nonInteractiveWidth = System.getenv("COLUMNS")?.toIntOrNull() ?: 120)` — `nonInteractiveWidth` подменяет только этот fallback и не трогает автоопределение/живой ресайз реального интерактивного терминала.

## Mordant `table {}`: собственное бюджетирование ширин вместо `Expand()` (Этап 7)

Пункт про `ColumnWidth.Expand()` выше **устарел как рекомендация** — Expand не годится для узких терминалов и в `scan`/`list` больше не используется. Проверено эмпирически на собранном бинаре (`ui/TableLayout.kt`, `ui/WorktreeTable.kt`):

- **`Expand()` схлопывается в 0, когда остатка нет.** `Expand()` отдаёт колонке *остаток* после Auto-колонок. На 80 колонках с большим портфелем остатка нет → колонка «Путь» получает нулевую ширину (`││`, `┬┐` в выводе — это и был баг). У Expand нет опции «минимальная ширина», это не настраивается. Решение: считать «естественные» ширины по plain-строкам сами, чистой функцией назначить каждой колонке ширину (`TableLayout.plan`), **пред-обрезать содержимое ячеек до передачи в таблицу**, отдать Mordant `ColumnWidth.Auto` — ужимать ему уже нечего. `whitespace = Whitespace.NORMAL` + `overflowWrap = OverflowWrap.ELLIPSES` на колонке пути оставить **как страховку** от ошибки расчёта на ±1 (видимая «…», а не молчаливая потеря).
- **Ширину считать по `String.length` на plain-строках ДО раскраски.** Цвет добавляет ANSI-байты, которые ломают подсчёт. Все глифы `✓ ● ⚠ …` — шириной 1. Проверка на артефакте: `awk '{print length}'` даёт **ложные срабатывания**, т.к. считает БАЙТЫ (рамки `─│` и кириллица — многобайтовые в UTF-8). Правильно мерить display-width через Python `unicodedata.east_asian_width`. Реальная таблица на `COLUMNS=80` укладывается ровно в 80 display-колонок.
- **Компактная таблица (Р3): `tableBorders` и `cellBorders` — разные оси.** `body { cellBorders = Borders.LEFT_RIGHT }` убирает горизонтальные линии МЕЖДУ строками тела — но в 3.0.1 заодно **срезает нижнюю рамку таблицы** (последняя строка тела остаётся без нижнего бордера). Лечится `tableBorders = Borders.ALL` на уровне таблицы: `tableBorders` рисует внешнюю рамку независимо от `cellBorders`. Итог: 27 worktree → 31 строка (рамка, заголовок, разделитель, 27 строк, рамка), а не 58.
- **Обрезка направлена по смыслу колонки.** Путь режется с сохранением ХВОСТА (`…/repo/worktree` — различающая часть в конце), имена репо/веток — с сохранением ГОЛОВЫ (`aiGitWorktreeMana…`). Дефолтный Mordant ELLIPSES режет только хвост, поэтому для путей бесполезен — обрезаем сами в `PathDisplay.truncateTail`. При выброшенной по ширине колонке «Orphaned» глиф `⚠` дописывается В КОНЕЦ ячейки ветки — и `truncateHead` его бы срезал; поэтому обрезается только имя ветки (до `w-2`), а ` ⚠` дописывается уже после.

## Clikt 5: терминал из контекста и тестируемость (Этап 7)

- **`context { terminal = ... }` вместо поля в каждой команде.** Раньше каждая `CliktCommand` держала `private val terminal = gwmTerminal()` — из-за этого вывод нельзя перехватить `CliktCommand.test(...)`. Правильно: в корневой команде `init { context { terminal = gwmTerminal() } }`, в командах — свойство `terminal` из `com.github.ajalt.clikt.core.terminal` (наследуется дочерними контекстами). `test(argv, ansiLevel = AnsiLevel.NONE, width = 80)` подменит терминал своим — так закрываются автотестом баги ширины/резолвинга (`ScanCommandTest`). Проверено: порядок применения `context {}` при `test()` работает, план Б (терминал параметром конструктора) не понадобился.
- **`currentContext.obj` (extension из `com.github.ajalt.clikt.core.obj`, НЕ метод `Context`).** В Clikt 5 у `Context` нет свойства `obj` — есть extension `getObj`/`setObj` и `findObject`. Родительский `run()` всегда выполняется до подкоманды: ставить `currentContext.obj = GwmGlobals(root)` **до раннего `return`** в корневом `run()`, иначе подкоманда увидит `null` (это и был баг «корневой `--root` молча игнорируется в `scan`»).
- **Одноимённая опция подкоманды затеняет корневую молча.** `gwm --root=X scan` и `gwm scan --root=Y` — это ДВЕ независимые опции с одним именем (`Gwm.root` и `ScanCommand.rootOpt`): Clikt разбирает опции после токена подкоманды её собственным парсером. Убрать любую нельзя (корневая нужна `--print-path`, у подкоманды — рабочая форма `scan --root`). Решение — свести все источники (позиционный `ROOT`, `scan --root`, корневой `--root`) к одному значению чистой функцией (`scan/RootSelection.kt`); разные непустые значения → `CliktError`, а не молчаливый приоритет.

## Опциональный конфиг: ручной TOML-подмножество вместо зависимости (Этап 8, PR 1/3)

`config/TomlLite.kt` — сознательно НЕ полноценный TOML: плоские `key = value`, массивы строк, одна секция `[name]` как префикс ключей; вложенные таблицы/массивы таблиц/даты/multiline-строки — явная `TomlParseException` с номером строки, а не молчаливое игнорирование. Причина — философия проекта (`docs/TECHNICAL_PLAN.md` §6, «локальный инструмент без лишних рантайм-зависимостей»): нужному конфигу (~10 строк) для полноценной TOML-либы нет оправдания.

- **`String?` из парсера ≠ «не задано».** Пустая строка (`key = ""`) — валидный, непустой `String?`. Любое место, где `null` означает «использовать дефолт» (здесь — `worktreePathTemplate`), должно проверять `?.takeIf { it.isNotBlank() }`, а не только `?: default` — иначе `template = ""` рендерится как реальный (пустой) шаблон: `File("")` резолвится в CWD процесса, а не в ожидаемое место. Баг найден на ревью, не тестами — ни один из юнит-тестов на `render()` не пробовал пустую строку отдельно от `null`.
- **`GwmConfig.load()` вызывается ОДИН раз**, в корневой `Gwm.run()`, до раннего `return` для `--print-path` (тот же паттерн, что у `--root`/`GwmGlobals` из Этапа 7) — подкоманды читают уже готовый `GwmConfig` из контекста, не парсят файл заново.
- **`--config <path>`** — не тестовый бэкдор, а полноценный видимый флаг (без `hidden = true`, с русским help), который заодно даёт тестам чистую точку внедрения (`@TempDir`-файл вместо реального `~/.config/gwm/config.toml`).
- **Тихий fallback ≠ отсутствие диагностики.** `roots[0]` из конфига — намеренно тихий fallback ниже `$GWM_ROOT` (см. `RootSelection`, не участвует в конфликт-детекции CLI-источников), но когда сконфигурированные `roots` заданы, а НИ ОДИН не существует (опечатка, размонтированный диск), это стоит явно предупреждать (stderr, exit остаётся 0), иначе опечатка в конфиге выглядит как «конфиг просто не сработал» без единой подсказки почему. То же для неизвестного имени цвета в `[colors]` — если в модуле есть `isKnown()`/аналог для детекции «неизвестное значение», проверить, что он реально ВЫЗЫВАЕТСЯ где-то с warning-побочным эффектом, а не просто существует и покрыт своим же тестом (было на ревью: `Colors.isKnown()` был написан, но нигде не вызывался — предупреждение из плана оказалось нереализованным).

## Группировка вывода `scan` по репозиторию (Этап 8, PR 2/3)

`ui/WorktreeTable.kt` схлопывает повтор имени репо в колонке «Репозиторий» на 2-й+ строке группы (`OverviewRow.repoIsGroupStart`) — реализовано как «соседние строки с одинаковым `repo` = одна группа», не как явная группировка по ключу.

- **Инвариант «соседние строки одного репо» — неявный контракт с `scan/ScanService.kt`**, не проверяется и не тестируется на стороне `WorktreeTable`. Держится на том, что `scanAsync` собирает результат через `flatMap` по репо (каждый репо — непрерывный блок worktree). Если когда-нибудь появится сортировка/фильтрация вывода (см. `POST_MVP_PLAN.md`) ПОСЛЕ скана, но ДО рендера, и она переставит строки не по репо — одно и то же имя репо может оказаться в двух разных местах таблицы, и группировка молча «сломается» (напечатает имя дважды вместо одного раза с пустыми строками между). Если такая фича появится — либо группировать явно по ключу (не по соседству), либо группировать уже ПОСЛЕ сортировки.
- **Флаг обязателен как источник истины для рендера**, не `plain.isEmpty()` на состоянии ячейки — репо-имя пустым в проде не бывает, но проверка "пустая ли строка" и "первая ли это строка группы" — два разных вопроса, которые легко перепутать при рефакторинге; `styledCell(REPO)` ветвится по `!r.repoIsGroupStart` явно.

## Ahead/behind + возраст worktree (Этап 8, PR 3/3)

Новые git-вызовы на каждый worktree в `WorktreeService.withAheadBehindAndAge` (по паттерну `withDirtyFlags`/`withOrphanStatus` — отдельный, дорогой опциональный шаг):

- **Семантика сторон `git rev-list --left-right --count`.** С диапазоном `HEAD...<branch>@{upstream}` git печатает `<ahead>\t<behind>` (ЛЕВОЕ = коммиты только в HEAD = ahead, ПРАВОЕ = только в upstream = behind) — **проверено эмпирически** на реальном репо (создан синтетический bare+clone с известным расхождением, дал `3\t2` для ahead=3/behind=2) и на портфеле сверкой с ручным `git`. Легко перепутать стороны — если меняете диапазон, перепроверяйте, не полагайтесь на память.
- **No upstream — это `git`-exit≠0 (код 128), а НЕ пустой вывод.** `fatal: вышестоящая ветка не настроена`. Обрабатывать по `GitResult.ok`, не по пустоте stdout, и не путать с «синхронно» (`0\t0` — валидный результат при наличии upstream, `null` — при его отсутствии, это два разных состояния).
- **Узкая проверка вместо широкой.** Изначально код превращал ЛЮБОЙ non-zero exit `rev-list` в `null` — это заодно проглатывало реальные git-ошибки (битые refs, upstream указывает на удалённую remote-ветку) под тем же `—`, что и обычное «нет upstream» (найдено на независимом ревью). Исправлено: сначала узкая проверка `hasUpstream(branch)` (уже существует, используется orphan-детекцией — `git rev-parse --abbrev-ref <branch>@{upstream}`), и только если она подтверждает upstream — вызывать `rev-list`. `hasUpstream` вызывается из `repoDir`, не из пути конкретного worktree — это безопасно: `@{upstream}`-трекинг хранится в общем `.git/config`, одинаков для всех worktree одного репо.
- **Возраст — из `%ct`, не `%cr`.** `git log -1 --format=%cr` локализован (на этой машине отдал «25 минут назад» по-русски) — непригодно для парсинга/ширины колонки. Берём unix-timestamp (`%ct`) и форматируем относительную давность сами (`ui/AgeFormat.kt`), локаль-независимо.
- **Производительность: +2 процесса на worktree, замерить, не гадать.** На реальном портфеле (25 репо/33 worktree, Этап 8 PR 3/3) — 54 новых git-вызова, но `time COLUMNS=200 gwm scan` до/после дал одинаковые ~1.4с: параллелизм по репо (Этап 4, coroutines) с запасом поглощает лишние процессы. Не распараллеливать worktree внутри репо превентивно — план явно предписывал «решать по факту замера», порог (>2× регресс) не был достигнут. Более дешёвый путь на будущее, если портфель вырастет — `git for-each-ref` батчем на весь репо вместо `rev-list`+`log` на каждый worktree (см. `docs/POST_MVP_PLAN.md`).
- **Деградация новых колонок — РАНЬШЕ, не позже структурных.** `ui/TableLayout.kt`: лестница `AHEAD_BEHIND → AGE → REPO → ORPHAN` (в порядке выброса), в отличие от Этапа 7 (`REPO → ORPHAN`). Новые колонки — необязательная информация, теряются первыми на узком терминале.

## Реальный мульти-корневой `scan` (Этап 9)

`scan` умеет агрегировать worktree из НЕСКОЛЬКИХ корней `config.roots` в один вывод. Реализация — `scan/MultiRootSelection.kt` (чистая логика) + `ScanService.dedupRepos` + развилка в `ScanCommand.run` (`Main.kt`).

- **Пусковой критерий — строгий и односторонний.** Мульти-корень включается ТОЛЬКО когда нет ни одного CLI-источника корня (позиционный `ROOT`, `scan --root`, корневой `gwm --root`) И не задан `$GWM_ROOT`. Любой явный ввод = однокорневой override, `config.roots` тогда игнорируется целиком (обратная совместимость с Этапами 7/8). Признак override в коде: `hasSingleRootOverride = chosen != null || !System.getenv("GWM_ROOT").isNullOrBlank()` — `$GWM_ROOT` проверяется ОТДЕЛЬНО от `resolveRoot`, т.к. для решения о развилке он считается override, хотя и не является конфликт-источником `RootSelection`.
- **Мульти-корень живёт НИЖЕ гейта `RootSelection`, отдельным объектом.** `RootSelection` намеренно про конфликт ЯВНЫХ CLI-вводов (разные значения → `CliktError`) и возвращает ОДИН `String?`. Объединение тихих fallback-корней — другая роль (множество корней, не конфликт), поэтому это `MultiRootSelection`, а НЕ расширение `RootSelection`. Смешивать обе роли в одном типе — испортить обе.
- **Два уровня дедупликации, оба по `absoluteFile.normalize().path`** (НЕ `canonicalFile` — лишний ФС-hit, разное поведение на разных ФС; симлинки осознанно не разрешаются): корни (`MultiRootSelection` — повтор пути в конфиге, `/x` vs `/x/`, `~/p` vs `$HOME/p`) и репозитории (`ScanService.dedupRepos` — один физический репо, достижимый из нескольких корней). Дедуп репо ОБЯЗАТЕЛЕН для инварианта группировки (`WorktreeTable`, PR 2/3): дубль репо напечатал бы его worktree дважды и мог «съесть» группировку, если между копиями попал одноимённый репо. `dedupRepos` — `companion`-функция (зовётся без экземпляра), вызывается в `ScanCommand`, НЕ внутри `scan()` — чтобы не менять плоский контракт `scan()` для существующих вызовов (`PrintPath`).
- **Порядок вывода не пересортировывается.** Корни — в порядке `config.roots`; внутри корня — репо по имени (`findRepos` уже сортирует); внутри репо — worktree как отдал git. Сбор — `rootsToScan.flatMap { findRepos(it) }` + `dedupRepos`. Глобальной пересортировки по имени репо через корни НЕТ — она сломала бы группировку (соседние строки одного репо). Одноимённые РАЗНЫЕ репо из разных корней (`~/work/foo` и `~/personal/foo`) оба печатаются как `foo` — не «съезд» (каждый блок непрерывен), а осознанный техдолг («уникальные подписи репо», связано с отложенной глобальной сортировкой).
- **Изоляция ошибок — всё warning (stderr, exit 0), не отказ.** Несуществующие корни из конфига → `ScanRoots.missing` → warning «пропущены несуществующие корни», scan идёт по существующим. ВСЕ корни отсутствуют → warning «ни один не найден» + дефолтный корень (обобщение предупреждения Этапа 8). Пустой конфиг → дефолт БЕЗ warning (нормальный случай). Пустой результат → «репозитории не найдены в: <перечень корней>». Единственные non-zero exit остаются прежними: конфликт CLI-корней (`RootSelection.Conflict`) и сломанный конфиг.
- **`base` для относительных путей: один корень → тот корень (пути относительные, как Этап 8); несколько → `null`** (общего базового каталога нет, `PathDisplay.shorten` даёт `~/…`/абсолютный). При одном существующем корне из конфига вывод БАЙТ-идентичен Этапу 8 (`roots[0]`-fallback) — иначе регресс.
- **`--print-path` тоже мульти-корневой (fix/print-path-multi-root).** Развилка override/мульти-корень вынесена из `ScanCommand.run` в чистую `MultiRootSelection.resolveRootsToScan(chosen, configRoots, env, home): ResolvedRoots` — общую для `scan` И `--print-path`. Функция НЕ печатает и НЕ бросает: диагностику (`missing`, `fellBackToDefaultFromMissing`, `singleRootOverride`) отдаёт полями, вызыватель сам решает поток и что считать отказом. `scan` → warning в stdout (`terminal.println`) + `CliktError` на несуществующий single/default-корень; `--print-path` → warning в **stderr** (`System.err`, НЕ stdout — его перехватывает `cd "$(...)"`), несуществующий корень НЕ отказ (пустой список репо → `Match.None` → `CliktError` выше). Shell-контракт `--print-path` цел байт-в-байт: при успехе stdout = сырой путь. Межкорневая коллизия имён (`root1/foo` vs `root2/foo`) в `--print-path` даёт `Match.Ambiguous` с различимыми путями — пользователь их отличит. `GwmConfig.primaryRoot()` больше НЕ имеет прод-вызывателей (был единственный — `PrintPath`); оставлен как чистый хелпер с юнит-тестом, кандидат на удаление. План — `docs/plans/fix-print-path-multi-root.md`.

## Ловушка сборки: `./gradlew build` не пересобирает `installDist`

`installDist` (задача `application`-плагина, кладёт бинарь в `build/install/gwm/bin/gwm`) **не** зависит от `build` по умолчанию — после `./gradlew build` бинарь в `build/install/` может быть устаревшим. Для ручной проверки поведения через собранный дистрибутив запускать `./gradlew installDist` явно (или `./gradlew build installDist` одной командой) перед прогоном `build/install/gwm/bin/gwm`.

## Тестирование

- **Юнит (без git, без TTY):** `WorktreeParser` и orphaned-эвристики — детерминированные таблицы вход/выход. `./gradlew test`.
